# 项目需求

学员从零开发一个基于 Web 的智能巡检机器人二维仿真系统。用户打开页面后，可以查看地图，发出移动指令，并看到机器人的位置、朝向和运行状态。完成基础版后，可继续实现自动巡检。

项目可个人完成，也可由 2–5 人组队完成。技术方案自行选择，普通电脑即可运行。计划完成的版本为 `XXX`，拟实现的功能范围为 `XXX`。

## 基础版（最低目标）

| 需求               | 验收方式                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| Web 界面与二维地图 | 打开页面，能看到至少一张二维地图，并辨认机器人和地图边界。若地图设置了障碍物，页面能区分障碍物与可通行区域。 |
| 后端 API           | 按接口说明发出请求，能获取地图或机器人状态，并能通过接口发送手动控制指令。                                   |
| 手动控制           | 在 Web 页面发出移动指令，机器人按指令移动。尝试越出地图边界时，机器人保持在地图内。                          |
| 状态反馈           | 操作后能在页面看到机器人更新的位置、朝向和运行状态。页面显示与 API 返回的状态一致。                          |
| Git 版本管理       | 提交可访问的项目仓库地址，能查看源码和开发过程中的提交记录。见[Git 协作与验收](#git-协作与验收)。            |
| 基础 CI            | 仓库能自动运行至少一项与项目相关的检查，例如测试或构建。能查看运行结果。                                     |
| Docker 部署        | 按文档执行 Docker 部署步骤，能打开页面并完成一次手动控制。                                                   |

## 标准版（推荐目标）

完成基础版后，可以按所选专项方向增加功能。个人或人数较少的小组完成所选方向的任务即可。组队时，每位成员按分工完成自己负责的任务。下表为可选功能及各自的验收方式，验收时按实际选定的任务核对。

| 需求         | 验收方式                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------- |
| 自动巡检     | 启动巡检后，机器人能按设定的顺序到达巡检点。页面能显示巡检是否完成。                               |
| 路径规划     | 给定起点和目标点，系统能生成绕开障碍物的可通行路径。目标点不可达时，系统能反馈结果。               |
| 虚拟传感器   | 实现至少一种仿真感知，例如前方障碍物检测。改变场景或机器人位置后，可以观察到感知结果随之变化。     |
| 简单异常处理 | 构造至少一种异常场景，例如目标不可达或移动受阻。系统能显示原因并停止相关操作，机器人状态仍可查看。 |

## 进阶版（自由拓展）

可按兴趣选择 AI 模型、Agent、更复杂的路径规划算法、机器人控制或其他工程化功能。进阶功能均为选做。选择拓展后，填写功能 `XXX`、解决的问题 `XXX` 和验证方式 `XXX`。

全栈、运维、算法、人工智能、嵌入式与具身智能等方向可作为选题和分工参考。

## Git 协作与验收

1. **使用自己的项目仓库。** 从模板创建个人或小组仓库后，首次推送前用 `git remote -v` 确认 `origin` 指向自己的项目仓库。小组成员在同一个项目仓库协作，PR 也以该项目仓库的分支为合并目标。
2. **按任务保存进度。** 完成一项功能、修复或文档更新后，检查差异并单独提交。标题写清具体改动，建议使用 `feat`、`fix`、`docs` 等前缀。验收时可以从提交记录看出项目的开发过程，提交次数由实际工作决定。
3. **按项目规模选择分支流程。** 个人项目可以直接向默认分支提交。小组项目建议先同步默认分支，再创建 `feat/manual-control` 这类短期任务分支。完成检查后用 PR 合并，在 PR 里写明改动、实际执行的检查和结果。遇到冲突时与相关成员核对后再合并。
4. **提交前检查文件和结果。** 确认提交只包含本次任务相关的文件，排除密码、令牌、本地依赖目录和可重新生成的构建产物。交付时确认验收人员能查看仓库、提交历史和基础 CI 的实际运行结果。小组成员的工作内容可结合[小组分工](02_小组分工.md)核对。

提交标题示例

```text
feat(frontend): 显示机器人当前位置
fix(backend): 阻止机器人移出地图边界
docs: 补充 Docker 部署步骤
```
